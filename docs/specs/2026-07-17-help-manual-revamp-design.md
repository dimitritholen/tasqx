# tasqx — Help / Terminal-Manual Revamp — Design

_Date: 2026-07-17. Status: approved (brainstorm). Not committed to git — this repo has no VCS; the spec is a file artifact._

## Problem

`tasqx`'s per-command help is generated by clap from doc-comments. Most commands carry **no examples** — e.g. `init`'s help never shows that you can pass a project name, so a real user (the project owner) did not discover `tasqx init keuken-verbouwen`. The only complete manual is `tasqx docs`, which is **browser-only** (a self-contained HTML file). There is no complete, example-rich, navigable manual **in the terminal**.

## Goal

1. Every command's `-h`/`--help` shows worked **examples**, plus notes and "see also".
2. A new top-level **`tasqx manual`** (alias `man`) renders a complete, themed, navigable manual in the terminal.
3. **Zero drift**: examples/summaries live in ONE registry that feeds clap help, the HTML `docs`, and the terminal manual; a build-time guard fails if the registry falls behind the CLI.

Non-goals: no change to the JSON API or core engine; this is a CLI presentation-layer change only. No pager. No full port of the 11-page HTML guide into the terminal.

## Decisions (locked in brainstorm)

- **D-a — Scope: both.** Rich per-command `-h` **and** a new `tasqx manual`.
- **D-b — `-h` shows everything.** Examples live in clap `after_help` (not `after_long_help`), so they appear on **both** `-h` and `--help`.
- **D-c — Single source + guard.** One `COMMAND_REF` registry feeds all three surfaces; the existing D15/D20 drift guards are extended to cover it.
- **D-d — No pager.** Navigation is the table-of-contents plus `tasqx manual <name>`. Cross-platform, dependency-free; matches the project's runtime-free ethos.
- **D-e — Division of labour.** `tasqx manual` = concise, navigable, in-terminal. `tasqx docs` stays the exhaustive browser guide; the manual points to it for the full reference.

## Architecture

### The registry — `crates/tasqx-cli/src/cmddoc.rs` (new)

One const table, `COMMAND_REF`, one record per CLI subcommand:

```
CmdDoc {
    verb:     &str,              // "init"
    aliases:  &[&str],           // [] or ["a", "new"]
    method:   &str,              // "project.create" (for the HTML docs table)
    summary:  &str,              // one line — the -h "about" / TOC line
    usage:    &str,              // "tasqx init <name> [--desc <text>]"
    examples: &[Example],        // Example { cmd: &str, note: Option<&str>, run: RunKind }
    notes:    &[&str],           // free-form caveats
    see_also: &[&str],           // ["use", "add", "projects"]
    topic:    Topic,             // which manual concept-section this verb belongs to
}
```

`RunKind` ∈ { `Safe` (idempotent/read-only, executed by the guard on a temp DB), `NoRun` (mutating / needs a daemon / illustrative — structurally checked only) }.

The registry lives in the CLI crate because it is help text (no core dependency).

### Surface 1 — clap `-h`/`--help`

Each `Command` variant gains `#[command(after_help = cmddoc::after_help("<verb>"))]`. `after_help()` returns a `String` built from that verb's record:

```
EXAMPLES
  tasqx init keuken-verbouwen
  tasqx init work --desc "Day job"
  tasqx init home && tasqx use home     # claim + set as default

NOTE  A project is just a name — no folder is created.
      init claims the default project only if the store has none.

See also: use · add · projects        Full manual: tasqx manual
```

- clap keeps rendering its own usage line + argument list (with its own colors); we inject only the block above.
- Plain text (no ANSI): survives a pipe, no fight with clap's color detection.
- `after_help` (not `after_long_help`) ⇒ shown on both `-h` and `--help` (D-b).
- The existing rich doc-comments on `Modify`/`Docs` are reconciled: their example lines move into the registry so there is one copy; the doc-comment keeps the conceptual prose as `long_about`.

### Surface 2 — `tasqx docs` (HTML), `docs.rs` (modified)

`docs.rs`'s `VERBS` table (verb, aliases, method, summary) is **derived from `COMMAND_REF`** instead of being a parallel const. The existing drift guard (`documented_verbs` == clap subcommands) is rewired to read the registry, not removed. Optionally the HTML per-command sections gain the registry's examples; at minimum the verb table stops being a second copy.

### Surface 3 — `tasqx manual` (new command + themed renderer)

New clap subcommand:

```
/// Browse the complete manual in your terminal (themed, navigable).
#[command(alias = "man")]
Manual { topic: Option<String> }   // command name, topic name, or none
```

- `tasqx manual` → themed **table of contents**: numbered concept-topics + a compact command index (verb → summary line). Footer points to `tasqx manual <name>` and `tasqx docs`.
- `tasqx manual <command>` → that command's full section (summary, usage, all examples, notes, see-also), themed.
- `tasqx manual <topic>` → a concept section. Topics: `getting-started, projects, capturing, dates, filters, reminders, reports, daemon, automation, json-api` (a concise mirror of the HTML guide's pages; the concept prose is short and points to `tasqx docs` for depth).
- Ambiguity rule: resolve `<name>` first against verbs/aliases, then against topic names; unknown → a `not_found`-style message listing valid names, exit 2 (`bad_request`) — never a silent empty page.
- Rendering reuses `theme.rs` (`Ctx`/`Caps`): colored on a truecolor/256/16 TTY, plain under NO_COLOR / when piped / on legacy Windows. No new color logic.
- Handled early in `main()` like `docs`/`theme`: **no store, no network** — a manual you can read when the store is broken.

### Where the themed renderer lives

Either a new `manual.rs` or a `render`/`manual` submodule of `cmddoc.rs`. Decided in the plan; the boundary is "registry data (`cmddoc`)" vs "themed layout of it (`manual`)".

## Drift guard (extends D15/D20)

New tests (in `cmddoc.rs`):

1. **Coverage** — `COMMAND_REF` has exactly one record per clap subcommand and vice-versa. Adding a verb without documenting it fails the build. (Same shape as the existing `DOCUMENTED_VERBS` guard, which is rewired to this registry.)
2. **Non-empty** — every record has a `usage` and ≥1 example.
3. **Executable (the honest guard)** — every `Example` with `RunKind::Safe` is **run against the real binary on a temp DB**, asserting exit 0. Per the handoff's hard-won lesson ("prefer a probe that would catch the bug over one that confirms the fix"), the manual's promises are executed, not merely present. `NoRun` examples are structurally checked only (parse as a `tasqx …` line, verb exists).
4. **`-h` contains its examples** — `tasqx <verb> --help` output contains each of that verb's example command strings.

Guard-authoring discipline from the handoff: when adding each guard, **revert the feature and watch it fail** before trusting it (scripted reverts have silently no-op'd here before). Assert `count == 1` on any string patch.

## Testing strategy

- Unit tests in `cmddoc.rs` for the four guards above.
- `manual.rs`: render each topic + a sample command section under a forced-plain `Caps` and assert key substrings (title, usage, first example) — deterministic, no TTY.
- Integration: drive the real binary — `tasqx init -h` shows the `init` examples; `tasqx manual`, `tasqx manual init`, `tasqx manual projects`, `tasqx manual bogus` (exit 2) all behave; piped output has zero ANSI escape bytes (reuse the D19 ESC-byte probe idiom).
- Full suite stays green from a **true clean rebuild** (`cargo clean -p tasqx-core -p tasqx-cli`), 0 warnings. Measure the test count from a real run; do not inherit it.

## Files

- **new** `crates/tasqx-cli/src/cmddoc.rs` — registry + `after_help()` + guards.
- **new** `crates/tasqx-cli/src/manual.rs` — themed TOC / section renderer (or a submodule of `cmddoc`).
- **modify** `crates/tasqx-cli/src/main.rs` — `after_help` on every variant; new `Manual` subcommand + early dispatch; register the new module(s).
- **modify** `crates/tasqx-cli/src/docs.rs` — derive `VERBS` from the registry; rewire the drift guard.

## Risks / watch-outs (from the session handoff notes)

- **Rebuild the binary before driving it** — `cargo build -p tasqx-cli`; `cargo test` does not refresh `target/debug/tasqx.exe`.
- **Incremental builds don't re-emit warnings** — `cargo clean -p …` before claiming 0 warnings.
- **`cargo test` stops at the first failing target** — use `--no-fail-fast` while iterating.
- **Tests have stayed green while the product was broken** — drive the real binary; prefer a probe that would catch the bug.
- **Backslashes/backticks mangle in Bash-tool heredocs and workflow `String.raw`** — build literals carefully; assert single-match on patches.
- **MSVC is discovered via vswhere, not PATH** — verify the toolchain by building, never `Get-Command`.
